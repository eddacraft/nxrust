## medium: External crate dependencies can be misclassified as internal project edges when names collide

id: fnd_sig-feat-library-f8bf0b65a1-3ae2_cc7a9f0c09
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Node source src (feat_library_f8bf0b65a1)

evidence:
- src/graph.ts:197-207 (createDependencies)
- src/graph.spec.ts:169-207 (createDependencies external dep test)
- src/graph.spec.ts:224-270 (createDependencies collision-adjacent test)

createDependencies checks projects[dep.name] before checking whether the dependency itself is external. In a workspace with project `util`, if another workspace package depends on a registry or git crate also named `util`, the dependency is emitted as `app -> util` instead of `app -> cargo:util`. That corrupts the Nx graph by adding a false internal workspace dependency and hiding the real external dependency edge. The included tests cover normal path dependencies, normal registry dependencies, and registry package entries that share a workspace package name, but not the direct dependency-name collision path that triggers this branch order bug.

recommendation:
In createDependencies, classify the dependency before the project-name lookup. Only emit an internal project edge when `!isExternal(dep, workspaceRoot)` and `projects[dep.name]` exists; for external dependencies, build `cargo:${dep.name}` and use ctx.externalNodes. Add the collision regression before changing the branch order.

test analysis:
The registry dependency test has only `app` in ctx.projects, so projects[dep.name] is false. The collision-adjacent test covers an external package entry that shares a workspace package name, not an external direct dependency whose name collides with a workspace project.

suggested regression test:
Add a createDependencies test where `app` depends on registry `util` while a workspace project named `util` also exists; assert the edge target is `cargo:util` and not `util`.

minimum fix scope:
Update createDependencies dependency classification and add one focused graph.spec.ts regression.

repro:
Mock cargo metadata with workspace packages `app` and `util`; make `app.dependencies` contain `{ name: "util", source: "registry+https://crates.io", kind: null }`; pass ctx.projects containing both `app` and `util` plus ctx.externalNodes containing `cargo:util`. createDependencies currently emits target `util` because the project-name lookup runs before external classification.

## medium: Inline publish token is passed through process argv

id: fnd_sig-feat-library-7beccade79-4d06_b6ca7c7abb
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Node source src/executors (feat_library_7beccade79)

evidence:
- src/executors/release-publish/executor.ts:36-41 (releasePublishExecutor)

The executor explicitly accepts an inline registry token and forwards it as a cargo command-line argument. The warning acknowledges that this leaks the secret into process listings, but the executor still performs the unsafe action, so a caller can expose a publish credential on shared CI runners or local multi-user systems.

recommendation:
Remove the token option from the executor contract, or reject it at runtime with a clear error and require CARGO_REGISTRY_TOKEN or another non-argv secret channel.

test analysis:
No linked tests were included for this feature, and the current code path intentionally appends the token to argv rather than asserting that token-based configuration is rejected.

suggested regression test:
Add a release-publish executor test that passes token and asserts the executor fails before calling cargoCommand, while a CARGO_REGISTRY_TOKEN environment-based path remains supported.

minimum fix scope:
Update src/executors/release-publish/executor.ts to stop forwarding options.token, and update any executor schema/docs/tests that advertise inline token support.

repro:
Invoke the release-publish executor with a token option; the resulting cargo publish command receives --token <secret> in argv.

## medium: release-publish accepts registry tokens in process arguments

id: fnd_sig-feat-library-86aef4e321-7a05_9e6fe44432
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Node package @eddacraft/nxrust (feat_library_86aef4e321)

evidence:
- src/executors/release-publish/executor.ts:8 (ReleasePublishExecutorSchema.token)
- src/executors/release-publish/executor.ts:35-42 (releasePublishExecutor)
- src/utils/cargo.ts:22-28 (cargoCommand)

The executor exposes a `token` option and, despite warning that it leaks, still passes the secret as `cargo publish --token <value>`. Redacting the console log only protects nxrust's own output; the token remains visible in process command-line inspection, CI process snapshots, shell/task telemetry, and any wrapper that records argv. A release executor should not provide a footgun for publishing credentials when Cargo already supports `CARGO_REGISTRY_TOKEN`.

recommendation:
Remove or reject the `token` option, or translate it into a child-process environment variable before spawning Cargo so the token is never placed on argv. Prefer documenting `CARGO_REGISTRY_TOKEN` as the only supported credential path.

test analysis:
No included release-publish tests are listed, and the available cargo argument tests focus on general argument construction rather than secret handling for the publish executor.

suggested regression test:
Add a release-publish executor test that passes `token` and asserts the spawned cargo argv never contains the token value; either expect an error or expect the token to be supplied via environment only.

minimum fix scope:
Update `src/executors/release-publish/executor.ts` and, if environment injection is chosen, the cargo process helper API used by `src/utils/cargo.ts`/`src/utils/run-process.ts`.

repro:
Configure or invoke `@eddacraft/nxrust:release-publish` with `{ "token": "secret" }`; while the process is running, inspect the cargo child command line and the token is present as the value following `--token`.

## medium: Cargo token redaction misses --token=<value> form

id: fnd_sig-feat-library-481f66376c-355f_38e49eb8bf
category: security
confidence: medium
triage: risk
status: open
feature: Node source src/utils (feat_library_481f66376c)

evidence:
- src/utils/cargo.ts:17-20 (cargoCommand)
- src/utils/cargo.ts:27-38 (redactArgs)

The command logger redacts only the split argv shape `--token <value>`. Cargo/clap-style flags also commonly accept `--token=<value>`, and that entire token is currently pushed to the log unchanged. A publish or login invocation using the equals form can therefore leak the secret into CI logs even though this helper explicitly tries to keep token values out of command output.

recommendation:
Extend redaction to recognise `--token=<value>` and emit `--token=***`; consider centralising secret flag handling for both split and equals forms.

test analysis:
The included tests cover cargo path classification only; there are no tests for `cargoCommand` logging or `redactArgs` secret handling.

suggested regression test:
Add a cargo utility test that exercises the redaction helper or a captured `cargoCommand` log for both `["--token", "secret"]` and `["--token=secret"]`, asserting the secret string is absent.

minimum fix scope:
Update `redactArgs` in `src/utils/cargo.ts` and add focused coverage for both supported token flag shapes.

repro:
Call `cargoCommand("publish", "--token=secret-value")`; the logged command includes `--token=secret-value` because `redactArgs` only matches an exact `--token` token followed by a separate value.

## medium: Release build can publish stale dist artifacts

id: fnd_sig-feat-release-51170e0f9c-df39_1a8a2ee2f9
category: build-release
confidence: medium
triage: risk
status: open
feature: Package script build (feat_release_51170e0f9c)

evidence:
- package.json:20-24 (files)
- package.json:37-38 (scripts.build)
- package.json:41-42 (scripts.prepublishOnly)

The package publishes broad dist globs, but the build script runs tsc and asset copying without first removing dist. TypeScript does not remove outputs for deleted or renamed source files, so a release run after such a change can leave obsolete JavaScript, declaration, JSON, or copied file assets under dist and include them in npm publish or npm pack. A separate clean script exists, but neither the build script nor the release scripts invoke it.

recommendation:
Make the release build start from a clean output directory, for example by changing build to run the clean step before tsc and copy-assets, or by adding a prebuild script that removes dist. Ensure prepublishOnly and release:dry-run use that clean build path.

test analysis:
No linked tests were provided for this feature, and the package scripts only run vitest after build; they do not assert package contents are free of stale dist files.

suggested regression test:
Add a packaging smoke test that creates a stale file in dist, runs the release build path, then verifies npm pack --dry-run or the generated package file list does not include the stale artifact.

minimum fix scope:
Update package.json build/release scripting so dist is cleaned before artifacts are generated, and add a focused packaging-content regression test.

repro:
Build once with a source or copied asset present, remove or rename that source/asset, then run pnpm build followed by npm pack --dry-run. The stale dist output can remain and be selected by the package files globs.

## medium: TypeScript build excludes generator template files that npm expects under dist

id: fnd_sig-feat-library-86aef4e321-86a2_37193f51b0
category: build-release
confidence: medium
triage: risk
status: open
feature: Node package @eddacraft/nxrust (feat_library_86aef4e321)

evidence:
- tsconfig.json:19-20
- package.json:17-18 (files)
- src/generators/crate/generator.ts:73-77 (crateGenerator)

The crate generator resolves templates from `__dirname/files/...`, which at runtime is `dist/generators/crate/files/...`. The TypeScript compiler explicitly excludes every `**/files/**` path, so those templates are not emitted by `tsc`; the package manifest only publishes `dist/**/files/**`, so a publish/build that does not copy templates into dist produces a package where `@eddacraft/nxrust:crate`, `:binary`, and `:library` fail at runtime when `generateFiles` cannot find the template directory. The `package.json` build script does run `tools/copy-assets.mjs`, but that script is outside the included evidence; the release-critical contract is split between an exclusion and an unverified custom copy step.

recommendation:
Make the template-copy contract explicit and tested: ensure `tools/copy-assets.mjs` copies `src/generators/**/files/**` into the matching `dist/generators/**/files/**` paths, and add a pack/build assertion that those directories exist. Alternatively, avoid relying on a separate untyped copy step by placing templates where the build/package pipeline includes them deterministically.

test analysis:
The listed generator tests run against source in the repository and do not demonstrate that the built npm artifact contains the runtime template directories under `dist`.

suggested regression test:
Add a release/pack test that runs `pnpm build`, inspects `dist/generators/crate/files/bin` and `dist/generators/crate/files/lib`, and invokes the crate/binary/library generators through the built entrypoints rather than source files.

minimum fix scope:
Validate or adjust `package.json`, `tsconfig.json`, and the asset-copy/build test path that owns generator templates.

repro:
Build or pack the package without a successful `tools/copy-assets.mjs` template copy, then run the crate generator from the packed package; `generateFiles` will look for `dist/generators/crate/files/bin` or `dist/generators/crate/files/lib` and those files are not produced by `tsc`.

## medium: Valid object-valued named input arrays are skipped instead of extended

id: fnd_sig-feat-library-4a2c94069d-2bd0_bab97828ee
category: bug
confidence: medium
triage: risk
status: open
feature: Node source src/generators (feat_library_4a2c94069d)

evidence:
- src/generators/init/generator.ts:73-83 (mergeNamedInput)
- src/generators/init/generator.spec.ts:30-45 (initGenerator cache named inputs)

Nx namedInputs arrays can contain non-string input definitions as well as strings. The generator currently only appends nxrust's canonical Rust cache patterns when every existing item is a string; if a consumer has a valid array containing an object input, initGenerator logs a divergence warning and leaves the array unchanged. That means a valid cache input configuration can fail to receive required Rust patterns, causing generated Rust projects to miss source/workspace files in Nx cache invalidation. The included tests cover string arrays and non-array values, but not mixed valid arrays, so this regression path is not protected.

recommendation:
Treat any array-valued named input as mergeable, append missing string patterns while preserving existing object entries, and only warn for non-array or otherwise unsupported namedInputs values.

test analysis:
The tests only exercise all-string arrays and a scalar string divergence case; they do not include a valid namedInputs array containing object entries.

suggested regression test:
Add a test where namedInputs.rustSources contains both a string and an object input, then assert missing Rust source patterns are appended and the existing object is preserved without a divergence warning.

minimum fix scope:
Update mergeNamedInput in src/generators/init/generator.ts and add a focused initGenerator spec for mixed array named inputs.

repro:
Create nx.json with {"namedInputs":{"rustSources":["{projectRoot}/src/**/*.rs",{"env":"RUSTFLAGS"}]}} and run initGenerator({skipFormat:true}); the generator will not append missing RUST_SOURCES_PATTERNS entries and will warn instead.
