# v0.2 Polish

Items surfaced during v0.1 review and shakedown that were deliberately
out of scope for the first release.

| ID | Owner | Status |
|----|-------|--------|
| POLISH | eddacraft | Proposed |

## Purpose

v0.1 shipped with a focused surface: seven executors, five generators,
a project-graph plugin. Several real gaps were identified during code
review and the consumer shakedown (module 01-v0.1-shakedown) but were
correctly deferred to keep v0.1 small and shippable.

This module collects those deferred items. None of them are urgent
enough to block v0.1, and none of them are part of monodon's surface
(those live in [02-monodon-parity](./02-monodon-parity.aps.md)). They
are nxrust-native polish — features that move nxrust from "works for
the v0.1 consumer's shape" to "works robustly across realistic
workspace variations".

## In Scope

**Graph robustness:**

- **Glob edge cases in workspace-member matching.** v0.1's
  `cargo metadata`-based graph plugin handles the canonical
  `workspace.members = ["crates/*"]` pattern. Edge cases not yet
  exercised: nested globs (`crates/**`), explicit members mixed with
  globs, `workspace.exclude` entries that prune members the glob would
  otherwise include, members with paths outside the workspace root via
  `path = "../..."` overrides.
- **Project-key vs cargo-name divergence handling.** v0.1 assumes Cargo
  package names map directly to Nx project keys (confirmed by R1's
  resolution note). The plugin currently fails ambiguously when the
  consumer wants a different Nx key — e.g. a Cargo package
  `my-crate-internal` exposed under the Nx key `my-crate`. Make this
  divergence explicit: either supported (option in the plugin config)
  or rejected (clear error pointing at the conflict).

**Executor surface:**

- **`cargo-nextest` executor.** A dedicated executor that invokes
  `cargo nextest run` when `cargo-nextest` is installed, with a
  graceful fallback message when it is not. The existing `test`
  executor already opportunistically uses nextest when available;
  separating it lets consumers opt in deliberately and configure
  nextest-specific options (test partitions, retries, junit output)
  without polluting the cargo-test schema.
- **`bench` executor for Criterion.** Wraps `cargo bench` with
  Criterion-aware defaults: directs Criterion's HTML report output
  somewhere Nx can cache, supports `--baseline`/`--save-baseline`
  pass-through, narrows `outputs` to the Criterion report directory
  rather than the entire `target/criterion/` tree.

**Generator surface:**

- **Dedicated library-only preset.** v0.1 ships a general-purpose
  `crate` generator (library by default, binary with `--bin`) and a
  separate `library` generator. A `preset`-style entrypoint that
  scaffolds a workspace specifically for library development — multiple
  library crates, no binary, doc-test wiring, README scaffolding — is
  a recurring ask from the libs-only consumer shape. This is distinct
  from monodon's `preset` (which is workspace-bootstrap; see
  [02-monodon-parity](./02-monodon-parity.aps.md)) — this one is a
  library-only workspace shape inside an existing workspace.

## Out of Scope

- napi / wasm-pack / monodon-style parity surface — those live in
  [02-monodon-parity](./02-monodon-parity.aps.md)
- Cross-compile matrix support (e.g. `--target` orchestration for
  multi-platform builds). Real ask, but a v0.3+ concern
- Semantic-release / changesets-driven release automation — flagged in
  module 01 as a v0.2 question but tracked as a release-process item,
  not part of this polish module
- Rewriting the v0.1 surface — polish is additive, not a redesign
- `crates.io` token validation for `release-publish` — already
  documented in the index as "unvalidated against a real token" and
  unblocks naturally when a consumer publishes

## Interfaces

### Depends On

- v0.1 surface stable on npm (`@eddacraft/nxrust@0.1.x`) — true as of
  module 01 completion (2026-05-12)
- A consumer workspace that exercises at least one of the polish items
  for validation — same constraint as v0.1: no work without a real
  validation target
- For `cargo-nextest` executor: a consumer with `cargo-nextest` in CI
- For `bench` executor: a consumer with Criterion benches checked in
- For glob edge cases: a consumer workspace using one of the
  non-canonical member patterns

### Exposes (at the end of this module)

- Additional executors registered in `executors.json`:
  `nextest`, `bench`
- Additional generator registered in `generators.json`:
  `library-preset` (or similar — name to be confirmed at promotion)
- Refined `createNodesV2`/`createDependencies` behaviour covering the
  glob and key-divergence edge cases, with regression tests in `spec/`
- README coverage for each new executor/generator at the same shape as
  the v0.1 entries

## Constraints

- **Zero regressions on the v0.1 surface.** Every executor, generator,
  and graph behaviour shipped in v0.1.x must continue to pass its
  existing tests. Polish is additive.
- **Each item ships independently.** A polish item is its own PR, its
  own CHANGELOG entry, its own minor or patch version bump as
  appropriate. Bundled "polish drops" are explicitly avoided.
- **Backwards compatibility on graph behaviour.** If the glob fixes or
  key-divergence handling change graph output for an existing consumer,
  call it out in CHANGELOG and bump the minor version, not patch.
- **Caching contract preserved.** New executors must follow the same
  `outputs` narrowing rule as the v0.1 surface — narrow `outputs`,
  cache reports not whole `target/` subtrees (per index risk table).
- **UK English in plan and README text; user-facing CLI output stays
  locale-neutral** (inherits index constraint).

## Ready Checklist

Change status to **Ready** for an individual item when:

- [ ] The item is reproducible against a real consumer workspace (not
      synthetic)
- [ ] An issue or note captures the consumer's exact failure mode or
      ask
- [ ] A Work Item has been drafted for the specific item being promoted
- [ ] The other items stay Proposed — promotion is per-item, not
      per-module

The module as a whole stays **Proposed** until at least one item
promotes. Multiple items may be Ready simultaneously, each as its own
Work Item.

## Risks & Mitigations

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| Glob fix changes graph output for an existing consumer | medium | medium | Bump minor version on graph-affecting fixes; call out in CHANGELOG; verify against v0.1 consumer workspace before publish |
| `cargo-nextest` executor diverges from `test` executor over time | medium | medium | Share the cargo-arg builder and options-allowlist logic between the two; one source of truth for cargo-test/nextest option translation |
| `bench` outputs caching bench artefacts that embed absolute paths | high | medium | Same playbook as v0.1 `target/` resolution: narrow `outputs` to report directories, verify cache-hit on a clean second run before release |
| Polish surface grows without bound | low | medium | Promotion gate above — each item promotes on a real consumer ask, not on speculation |
| Library-only preset overlaps monodon's `preset` generator | low | low | Different scope (in-workspace shape vs. fresh workspace bootstrap); name disambiguates; cross-link the two modules at promotion |

## Decisions

- **D-PL1:** Promotion is per-item, not per-module. Each polish item
  has its own real-consumer trigger. *Accepted.*
- **D-PL2:** Graph-behaviour-changing fixes bump the minor version,
  not patch. Consumers should be able to pin patch versions and trust
  that graph shape is stable within a minor line. *Accepted.*

## Open Questions

- [ ] Should `cargo-nextest` replace `test` once it's stable, or stay
      a sibling? Replacing breaks consumers without nextest installed;
      keeping both grows the surface. Defer to promotion time.
- [ ] Where do Criterion HTML reports live in the cached outputs? Per
      crate (`<project-root>/target/criterion/`) versus per workspace
      (`<workspace-root>/target/criterion/`). The cargo workspace
      layout in v0.1 puts `target/` at the workspace root, but
      Criterion's convention varies. Resolve at promotion.
- [ ] Library-only preset: is this in `generators.json` as
      `library-preset`, or is it the existing `library` generator with
      a `--preset` flag? Resolve at promotion based on the consumer's
      invocation shape.
- [ ] When project-key vs cargo-name divergence is supported, where
      does the mapping live? Plugin options in `nx.json`, per-crate
      `project.json` override, or a top-level `nxrust.json`? Resolve
      at promotion, with a bias toward `nx.json` plugin options for
      consistency with how the plugin is already registered.
